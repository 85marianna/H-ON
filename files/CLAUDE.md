# H-ON VBA 매크로 프로젝트 작업 규칙

## 1. 프로젝트 목적

이 폴더에는 H-ON 회계 시스템 및 업무 자동화에 사용되는 Excel VBA 매크로 파일이 있다.

현재 주요 목적은 기존에 정상적으로 작동하는 매크로를 최대한 유지하면서 전체 코드를 점검하고 리팩토링하는 것이다.

리팩토링의 목표는 다음과 같다.

* 불필요한 코드 제거
* 중복 코드 정리
* 복잡한 코드 단순화
* 공통 기능의 함수화
* 프로시저의 역할과 책임 명확화
* 가독성 개선
* 변수 및 프로시저 이름의 일관성 확보
* 오류 처리 방식 정리
* 유지보수하기 쉬운 구조로 개선
* 코드만 보아도 업무 로직을 이해할 수 있도록 개선

**새로운 코드로 전면 재작성하는 것이 목적이 아니다.**

---

# 2. 최우선 원칙 — 기존 코드와 기능 보호

## 2.1 현재 작동하는 코드를 최대한 유지한다.

현재 정상적으로 작동하는 코드와 업무 로직을 임의로 변경하거나 새 방식으로 전면 재작성하지 않는다.

리팩토링의 기본 원칙은 다음과 같다.

> **기존 기능과 결과를 유지하면서 코드의 구조와 품질을 개선한다.**

단순히 새로운 방식이 더 깔끔하거나 최신 방식이라는 이유만으로 기존 코드를 변경하지 않는다.

기존 코드에 특별한 문제가 없다면 그대로 유지하는 것을 우선한다.

---

## 2.2 기존 변수명을 임의로 변경하지 않는다.

현재 사용 중인 변수명은 특별한 이유가 없는 한 변경하지 않는다.

특히 다음 항목은 임의로 변경하지 않는다.

* 변수명
* 함수명
* Sub 프로시저명
* UserForm 이름
* 컨트롤 이름
* Worksheet 이름
* Workbook 이름
* DB 테이블명
* DB 필드명

가독성을 위해 이름 변경이 필요하다고 판단하더라도 먼저 프로젝트 전체에서 해당 이름의 사용처와 의존 관계를 확인한다.

**"이 변수명이 마음에 들지 않는다"는 이유만으로 변경하지 않는다.**

---

## 2.3 기존 프로시저와 함수의 역할을 먼저 파악한다.

코드 일부만 보고 해당 코드가 불필요하다고 판단하지 않는다.

수정 또는 삭제 전에 다음 사항을 확인한다.

* 다른 프로시저에서 호출되는지
* 다른 모듈에서 사용하는지
* UserForm에서 사용하는지
* 다른 파일에서 호출되는지
* 특정 업무 상황에서만 실행되는지
* DB 또는 외부 파일과 연결되어 있는지
* 특정 회계 업무 규칙과 관련되어 있는지

사용 여부가 확실하지 않은 코드는 임의로 삭제하지 않는다.

---

# 3. 리팩토링과 기능 변경을 구분한다.

리팩토링과 기능 추가 또는 업무 로직 변경을 가능한 한 분리한다.

### 리팩토링

기존 기능과 결과는 유지하면서 다음을 개선한다.

* 코드 구조
* 중복
* 가독성
* 유지보수성
* 오류 가능성
* 코드의 역할 분리

### 기능 변경

다음과 같은 변경은 단순 리팩토링으로 간주하지 않는다.

* 계산 결과 변경
* 업무 규칙 변경
* DB 구조 변경
* 출력 결과 변경
* 파일 생성 방식 변경
* SAP 업로드 방식 변경
* 기존 사용자 동작 변경

기능 변경이 필요하다면 기존 로직을 먼저 설명하고 변경 이유와 영향을 확인한다.

---

# 4. 리팩토링 작업 순서

코드를 수정하기 전에 먼저 전체 구조를 파악한다.

권장 작업 순서는 다음과 같다.

1. 전체 프로젝트 구조 확인
2. VBA 모듈 및 UserForm 목록 확인
3. 주요 프로시저와 함수 확인
4. 프로시저 간 호출 관계 확인
5. 데이터 흐름 확인
6. DB 및 외부 파일 의존 관계 확인
7. 사용되지 않는 코드 후보 확인
8. 중복 코드 확인
9. 복잡하거나 지나치게 긴 프로시저 확인
10. 리팩토링 대상 선정
11. 최소 범위로 수정
12. 기존 기능 테스트
13. 결과 확인
14. 다음 리팩토링 대상으로 이동

한 번에 너무 많은 코드를 변경하지 않는다.

가능하면 하나의 변경 목적을 하나의 작업 단위로 처리한다.

---

# 5. 불필요한 코드 정리

다음과 같은 코드는 우선적으로 검토한다.

* 사용되지 않는 변수
* 사용되지 않는 프로시저
* 사용되지 않는 함수
* 호출되지 않는 코드
* 중복된 코드
* 과거 테스트를 위해 남겨둔 코드
* 더 이상 사용하지 않는 주석 처리 코드
* 불필요한 `Debug.Print`
* 불필요한 `Select`
* 불필요한 `Activate`
* 동일한 기능을 여러 곳에서 구현한 코드
* 의미 없이 반복되는 코드
* 더 이상 사용하지 않는 임시 변수

단, **실제 사용 여부가 확실하지 않은 코드는 바로 삭제하지 않는다.**

프로젝트 전체에서 참조 여부를 확인하고 다른 기능에 영향을 주지 않는지 확인한 후 삭제한다.

---

# 6. 주석 처리된 오래된 코드

과거 코드를 단순히 주석 처리하여 보관하는 방식은 지양한다.

예:

```vba
'Old Code
'Set rs = ...
'rs.Open ...
'...
```

Git을 통해 이전 버전의 코드를 확인할 수 있으므로 더 이상 필요하지 않은 코드는 삭제를 우선 검토한다.

단, 삭제 전에 실제 사용 여부와 영향 범위를 반드시 확인한다.

---

# 7. 중복 코드 정리

동일하거나 유사한 로직이 여러 곳에 존재한다면 공통 함수 또는 프로시저로 통합할 수 있는지 검토한다.

특히 다음 영역은 공통화 가능성을 우선적으로 검토한다.

* DB 연결
* DB 조회
* 데이터 필터링
* 파일 존재 여부 확인
* 파일 저장
* 폴더 생성
* 데이터 검증
* 공통 값 설정
* 계정 및 부서 매핑
* 업로드 파일 생성
* 오류 처리

단순히 코드의 길이를 줄이는 것이 목적이 아니다.

**코드의 역할과 책임이 명확해지는 방향으로 리팩토링한다.**

---

# 8. 프로시저 구조 개선

하나의 프로시저가 지나치게 많은 역할을 담당한다면 적절하게 분리한다.

예를 들어 하나의 프로시저가 다음 작업을 모두 수행하고 있다면:

```text
데이터 조회
→ 데이터 검증
→ 계산
→ 결과 생성
→ 파일 저장
→ 사용자 메시지 표시
```

각 역할을 적절한 함수 또는 프로시저로 분리할 수 있는지 검토한다.

다만 무조건 잘게 쪼개지 않는다.

**하나의 함수 또는 프로시저가 하나의 명확한 책임을 갖는 것**을 목표로 한다.

---

# 9. 주석 작성 규칙

리팩토링 과정에서 기존 주석도 함께 검토한다.

## 9.1 기존의 의미 있는 주석은 유지한다.

기존 코드에 작성되어 있는 업무 규칙이나 중요한 설명은 함부로 삭제하거나 축약하지 않는다.

특히 다음과 관련된 주석은 중요하게 유지한다.

* 회계 처리 기준
* 업무 규칙
* 특정 계정 처리
* 특정 날짜 처리
* SAP 업로드 규칙
* DB 처리 이유
* 예외 처리 이유
* 향후 수정 시 주의사항

---

## 9.2 주석은 "무엇"보다 "왜"를 설명한다.

코드만 읽어도 알 수 있는 내용을 반복해서 설명하는 주석은 작성하지 않는다.

### 좋지 않은 예

```vba
'다음 달 1일을 계산한다.
ReverseDate = DateSerial(Year(EvalDate), Month(EvalDate) + 1, 1)
```

### 좋은 예

```vba
'중간결산 평가금액은 다음 달 1일에 역분개하여
'다음 기간의 장부금액에 영향을 주지 않도록 한다.
ReverseDate = DateSerial(Year(EvalDate), Month(EvalDate) + 1, 1)
```

---

## 9.3 주석을 추가해야 하는 경우

다음과 같은 경우에는 적절한 주석을 추가한다.

* 회계 업무 규칙이 코드만으로 이해하기 어려운 경우
* 특정 계정이나 날짜에 대한 예외 규칙이 있는 경우
* SAP 업로드를 위한 특수한 처리
* DB 구조 때문에 특정 방식으로 처리하는 경우
* 다른 코드만으로는 이유를 알기 어려운 경우
* 성능 또는 호환성 때문에 특정 방식을 사용하는 경우
* 향후 수정 시 주의해야 하는 경우

주석은 가능한 한 **업무적인 이유와 코드의 의도**를 설명한다.

# 10. VBA 코드 작성 원칙

가능하면 다음 원칙을 따른다.

* `Option Explicit` 사용
* 의미 있는 변수명 사용
* 기존 프로젝트의 변수명은 가능한 한 유지
* 의미 있는 프로시저명 사용
* 적절한 데이터 타입 사용
* 불필요한 `Variant` 사용 최소화
* 반복되는 로직 함수화
* 불필요한 `Select`, `Activate` 지양
* 적절한 오류 처리 적용
* 기존 프로젝트의 공통 함수를 우선 활용

새로운 코딩 스타일을 적용하기 전에 기존 프로젝트의 스타일과 구조를 먼저 확인한다.

**기존 코드와 새로운 코드가 서로 다른 스타일로 혼재되지 않도록 한다.**

---

# 11. DB 및 외부 파일 처리

DB, 파일 경로, 외부 시스템과 관련된 코드는 특히 주의한다.

다음 항목은 임의로 변경하지 않는다.

* DB 테이블명
* DB 필드명
* DB 연결 방식
* 파일 경로 규칙
* 파일명 규칙
* 업로드 파일 형식
* SAP 업로드 구조
* 기존 데이터 구조

변경이 필요한 경우 기존 사용처와 영향 범위를 먼저 확인한다.

---

# 12. 테스트 원칙

리팩토링 후에는 기존 기능이 동일하게 작동하는지 확인한다.

가능하면 다음 상황을 포함하여 테스트한다.

* 정상적인 데이터
* 데이터가 없는 경우
* `Null` 값
* 빈 문자열
* 0 값
* 날짜 경계값
* 파일이 존재하지 않는 경우
* DB 연결 실패
* 잘못된 입력값
* 기존 업로드 파일 생성 결과

리팩토링 전과 후의 결과가 달라지는 경우 원인을 확인한다.

---

# 13. 변경 범위 관리

코드를 수정할 때는 가능한 한 변경 범위를 작게 유지한다.

한 가지 문제를 해결하기 위해 관련 없는 코드까지 함께 수정하지 않는다.

특히 다음과 같은 변경은 피한다.

* 요청하지 않은 변수명 전체 변경
* 요청하지 않은 프로시저명 변경
* 전체 코드 스타일 일괄 변경
* 정상 작동하는 로직의 전면 재작성
* 기능과 관계없는 대규모 구조 변경
* 한 번에 여러 기능을 동시에 수정

**작은 단위로 변경하고 확인하는 방식을 우선한다.**

---

# 14. Git 및 변경 관리

중요한 리팩토링을 시작하기 전 현재 정상 작동 상태를 Git에 커밋하는 것을 권장한다.

예:

```text
chore: 리팩토링 전 정상 작동 상태 저장
```

리팩토링 후에는 변경 목적이 명확하게 드러나는 커밋 메시지를 사용한다.

예:

```text
refactor: 중복된 DB 조회 로직 공통 함수로 통합
refactor: 휴지비 대체 집계 로직 분리
cleanup: 사용하지 않는 테스트 코드 제거
fix: Null 데이터 처리 오류 수정
```

기능 추가와 리팩토링을 하나의 커밋에 지나치게 많이 섞지 않는다.

# 15. Claude Code 작업 방식

Claude Code는 코드를 수정하기 전에 현재 구조와 로직을 먼저 분석한다.

사용자가 특정 코드의 수정을 요청하더라도 해당 코드가 다른 기능에서 사용되고 있는지 확인한다.

수정 범위가 넓어질 가능성이 있다면 영향을 받는 부분을 먼저 확인한다.

사용 여부가 불확실한 코드를 임의로 삭제하지 않는다.

기존 변수명이나 프로시저명을 임의로 변경하지 않는다.

기존 기능을 유지할 수 있는 방법을 우선적으로 선택한다.

새로운 구현 방식이 더 좋아 보인다는 이유만으로 기존 코드를 전면 재작성하지 않는다.

---

# 16. 리팩토링의 판단 기준

코드를 변경하기 전에 다음 질문을 먼저 확인한다.

1. 왜 이 코드를 변경해야 하는가?
2. 현재 코드에 실제 문제가 있는가?
3. 기존 기능에 영향을 주는가?
4. 기존 코드보다 무엇이 좋아지는가?
5. 더 작은 범위의 수정으로 해결할 수 있는가?
6. 기존 변수명과 프로시저명을 유지할 수 있는가?
7. 이 변경이 정말 필요한가?

위 질문에 대한 답이 명확하지 않다면 **기존 코드를 유지하는 것을 우선한다.**

---

# 17. 최종 목표

이 프로젝트의 리팩토링 목표는 단순히 코드를 짧게 만드는 것이 아니다.

**현재 정상적으로 작동하는 업무 시스템을 안정적으로 유지하면서,**

* 불필요한 코드는 제거하고
