## 2. 재고 관리 시스템 유산 (오빠두엑셀 기원)

### 2.1 완전히 주석 처리된 모듈

**`Mod_WS.bas` (266줄) — 전체가 `''`로 주석 처리**
- 원래 목적: 워크시트 기반 재고 관리 로직
- 현재 상태: **전부 비활성화** (코드는 남아있으나 실행 불가)
- 포함된 코드:
  - 재고 관련 변수, 입출고 폼 열기 (`OpenfrmProduct`, `OpenfrmInventorySearch` 등)
  - 재고 데이터 CRUD 프로시저
  - 회계 전표 입력 로직 (현재는 폼 기반으로 이동됨)

**→ 완전히 제거 가능한 후보** (사용 흔적 0%, 현대체 이미 존재)

### 2.2 비활성 폼들

**`frmProduct.frm`** (282줄)
- 기능: 제품 정보 등록/편집/삭제
- 상태: 정의만 있고 어디서도 호출되지 않음
- 관련: `frmProductSelect.frm`과 함께 재고 시스템의 일부
- **→ 삭제 가능성 높음** (현재 회계시스템에서 사용 안 함)

**`frmProductSelect.frm`** (88줄)
- 기능: 제품 선택 팝업
- 상태: 호출 흔적 없음
- **→ 삭제 가능성 높음**

### 2.3 잔존하는 재고 용어

코드에서는 보이지 않지만 논리적 유산:
- `frmProduct` 폼: 단순히 있는 것 (실제로는 회계시스템에서 필요 없음)
- 초기에 거래처/계정 관리가 제품 관리 패턴을 모방한 것으로 보임
  - `frm거래처관리`, `frm계정검색` 등이 `frmProduct` 구조를 확대 적용

## 4. 중복 코드 분석

### 4.1 DB 연결 관련 중복

**현황**:
- `ConnectAccessDB()` (Mod_ACCESS.bas) — 공개 함수
  - 호출처: `Mod_ACCESS.bas` (2회), `frmMain.frm` (2회)
- `Mod_ACCESS_DB.bas` — 1,171줄의 거대한 단일 모듈
  - 다양한 DB 조회 프로시저들이 개별 구현

**문제점**:
- 같은 DB에 접근하는 여러 프로시저들이 비슷한 연결 코드를 반복
- 특정 테이블에 대한 CRUD 로직이 산재 (예: 전표, 거래처, 계정 등)

**개선 방향**:
- `Mod_ACCESS_DB.bas`를 기능별로 분할 고려
  - 예: `Mod_Voucher_DB`, `Mod_Customer_DB`, `Mod_Account_DB` 등
- 공통 DB 연결 래퍼 강화

### 4.2 보고서 생성 관련 중복

**현황**:
- `HJ_Mod_Report.bas` (1,039줄) — 합계잔액시산표 (엑셀 시트 기반)
- `Mod_ACCESS_Report.bas` (919줄) — 합계잔액시산표 (DB 기반)
- `Mod_ACCESS_Report_BS.bas` (598줄) — 재무상태표
- `Mod_ACCESS_Report_PL.bas` (563줄) — 손익계산서

**문제점**:
- 같은 보고서를 두 가지 방식으로 생성 (워크시트 vs DB)
- 각 보고서 모듈이 유사한 포맷팅/계산 로직을 반복 구현
- 헤더, 소계 행, 합계 계산 로직이 각 모듈에 분산

**개선 방향**:
- 통일된 보고서 생성 엔진 구축 고려
- 공통 포맷팅 함수 추출
- `HJ_Mod_Report`와 `Mod_ACCESS_Report` 중 하나로 통합

### 4.3 폼 컨트롤 처리 관련 중복

**현황**:
- `z_Mod_Frm.bas` — 리스트박스, 콤보박스, 폼 유틸함수 집중
  - 512줄, 다양한 `Update_Cbo`, `Update_List`, `Select_CboItm` 등
- 각 폼에서 비슷한 컨트롤 초기화 로직 반복

**개선 방향**:
- `z_Mod_Frm.bas` 구조는 이미 적절히 중앙화되어 있음 (유지 권장)

### 4.4 유틸 함수 모듈들

**현황**:
- `z_Mod_Array.bas` (304줄) — 배열 조작
- `z_Mod_DB.bas` (669줄) — 워크시트 DB 유틸
- `z_Mod_Sort.bas` (174줄) — 정렬
- `z_Module_GetCursor.bas` (64줄) — 마우스 커서
- `z_Module_ListWheel.bas` (118줄) — 마우스휠로 리스트박스 스크롤
- `z_Mod_Shape.bas` (65줄) — 도형 처리

**평가**:
- 각 모듈이 명확한 책임을 가짐 (좋음)
- 다만, 일부 함수가 더 이상 사용되지 않을 가능성
  - 예: `z_Mod_DB.bas`의 함수들은 원래 워크시트 기반 시스템용이었으나, 현재는 ACCESS DB 중심

## 6. 핵심 재구축 영역

### 6.1 DB 계층 (Mod_ACCESS_*.bas)

**현황**:
- `Mod_ACCESS_DB.bas` (1,171줄) — 지나치게 큼
- 다양한 테이블(전표, 거래처, 계정 등)의 쿼리가 혼재

**제안**:
1. 테이블별로 별도 모듈로 분할
   - `Mod_Voucher_DB` — 전표 CRUD
   - `Mod_Customer_DB` — 거래처 CRUD
   - `Mod_Account_DB` — 계정 CRUD
   - 등등
2. 공통 DB 연결/에러 처리를 `Mod_ACCESS_Common`으로 추출

### 6.2 보고서 생성 (HJ_Mod_Report.bas vs Mod_ACCESS_Report.bas)

**현황**:
- 두 가지 경로 존재 (의도적인 것일 수 있음 — 확인 필요)
  - 워크시트 기반: `HJ_Mod_Report.bas`
  - DB 기반: `Mod_ACCESS_Report.bas` + `Mod_ACCESS_Report_BS/PL.bas`

**제안**:
1. 사용자 입장에서 어느 쪽이 권장인지 확인
2. 향후 전환 계획이 있다면 명시 (예: DB 기반으로 통일)
3. 현재는 **양쪽 모두 유지** (리팩토링 시 신중)

### 6.3 워크시트 기반 DB 유틸 (z_Mod_DB.bas)

**현황**:
- 669줄로 상당히 큼
- 원래는 워크시트를 DB처럼 사용하던 시대의 유산
- 현재 ACCESS DB 중심이 되며 사용 빈도 감소

**제안**:
- 각 함수의 실제 사용처를 파악한 후 선별적 정리
- 일부는 `z_Mod_Array.bas`로 통합 검토
